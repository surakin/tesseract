**H5. Decrypted content and attachment keys are stored in plaintext side databases**

`sdk/src/client/backfill.rs:1029-1175` (`open_app_cache_db`, `open_search_db`, `open_thread_read_db`), `client/room_media_store.rs:27-56`, `client/search.rs`.
The matrix-sdk stores are opened with a per-account `store_key`, but Tesseract's own SQLite files in the same directory are opened with plain `rusqlite::Connection::open` — no key, default file mode:
- `search_index.db` — full decrypted message bodies, senders and timestamps of E2EE rooms (opt-in, but the opt-in does not mention that the store encryption is bypassed).
- `app_cache.db` / `room_media` — captions, filenames, and for encrypted attachments **`src_json`/`thumb_json`, i.e. the whole `EncryptedFile` including the AES key, IV and hashes**; plus room summaries, export checkpoints (output paths), last-message previews.
Anyone who can read the data directory can decrypt the user's E2EE attachments from the media repo and read indexed history, defeating the point of encrypting the SDK store.

**Fix:** encrypt these databases with the same `store_key` (SQLCipher / `rusqlite` `bundled-sqlcipher`, or store sensitive columns encrypted with a key derived from `store_key`), stop persisting `src_json` for encrypted media (re-derive from the event), create files `0600`, and state the limitation in the search-indexing setting text until fixed.
- Status: **Not done** (deferred by the owner)

**H7. Soft-logout recovery always fails for store-key accounts and then **deletes the account's crypto store****

`ui/shared/app/ShellBase_accounts.cpp:1707-1750` (`handle_sync_error_impl_`, context `sync_auth_error`).
For a soft logout it reads the credentials with `SessionStore::load_account(uid)` and passes the string to `restore_session`. `load_account` returns the **raw SecretStore blob**; for every account created since store encryption was added that blob is the wrapper `{"tesseract_store_key_wrapper":true,"session":…,"store_key_hex":…}` (`session_store.cpp:694-719`). The code in `restart_sdk_begin_` (`:1423-1431`) even documents that `restore_session` "chokes on it (missing field `client_id`)" and uses `load_account_with_key` there — this call site was missed. Result: `restore_session` fails, control falls into "Unrecoverable", which calls `SessionStore::clear_account(user_id)` — removes the keychain entry **and `fs::remove_all(account_dir)`**, i.e. the device's cross-signing keys and every un-backed-up Megolm key — and asks for a fresh login. A soft logout (token expiry, MAS session refresh problems, an admin forcing re-auth) was supposed to be recoverable without data loss.
Also: the recovery path runs `restore_session` (network + SQLite open) on the **UI thread**, and the "not soft logout" branch wipes local data with no confirmation (a server-side session revocation doesn't need local key destruction; the user may still want to export keys).
**Fix:** use `load_account_with_key` + `set_store_key` (as `restore_all_accounts_blocking_` does), run it on `mut_pool_`, never `clear_account` automatically: keep the store and offer "Sign in again" (reusing the device id where the server allows) — only delete on explicit sign-out.
- Status: Fixed for soft logout (stored store key, off the UI thread, never wipes on failure). **Not done:** a hard logout (revoked session) still clears the account and relogs in, because the shells' relogin path signs the account out

**M45. Account switch / sign-out during a call is not handled (dangling `Client*`, frames to the wrong account)**

`ShellBase_calls.cpp:392` builds `CallSession(client_, …)` with the raw `Client*` of the account active at call start, and the capture callbacks dereference the shell's *current* `client_` (`:241`, `:324`). Nothing in `ShellBase_accounts.cpp` (switch, `logout_active_account_impl_`, `sign_out_active_account_`) checks `call_session_`/`active_call()` or ends the call — the only call guards in the app are in `clear_all_caches_` (`ShellBase_media_fetch.cpp:999`) and `restart_app_` (`ShellBase_profile.cpp:195`). Consequences: (a) after switching accounts, camera/screen frames are pushed into the *new* account's client while the session lives on the old one (frames silently lost, or an RTC call on the wrong client); (b) signing out the calling account destroys its `Client` while `CallSession` still holds the raw pointer → use-after-free in `hang_up()`/`~CallSession`; (c) the capture threads read `client_` (a plain member mutated on the UI thread) without synchronisation, and `:324` has no null check, so a logout racing a camera frame dereferences null. **M49. Call video/screen frames are posted to the UI thread without back-pressure**

`EventHandlerBase.cpp:1075-1177`: every decoded remote video/screen frame is converted to a freshly allocated BGRA `std::vector` (≈8 MB at 1080p) on the SDK worker thread and posted with `post_to_ui_`. There is no "latest frame wins" coalescing per participant, so if the UI thread is busy (relayout, GTK idle starvation, a slow `MUT_FFI` freeze from M42/M43/M48) frames queue unbounded: tens of MB per second of memory growth plus stale video once the UI catches up. Keep one pending frame slot per participant (atomic swap) and post at most one UI task per participant until it is consumed. Also guard `n_px * 4 <= rgba_size` before the conversion loops (`:1094-1117`, `:1144-1167`): the loops index `rgba[i*4+3]` for `n_px = width*height` pixels but only `rgba_size` bytes are known to exist, so an inconsistent (width, height, size) triple from the Rust side reads/writes out of bounds.
- Status: Partial: one pending frame per participant and stream, with at most one UI task each. The size check rejects frames whose bytes do not fit. **Not done:** the per-frame allocation

**M55. UnifiedPush registration discards the per-device endpoint and uses a lossy, predictable pushkey**

`ui/shared/linux_up_connector_core.cpp:96-168,222-236` + `sdk/src/client/notifications.rs:415-441`: `on_new_endpoint` normalises the endpoint to `https://<authority>/_matrix/push/v1/notify` — path and query (the part that identifies *this* client at the push provider) are thrown away — and `register_pusher` is called with `pushkey = sanitize_token(user_id)`, i.e. the MXID with every non-alphanumeric byte mapped to `_`. As I read the UnifiedPush Matrix-gateway spec the convention is `pushkey = <the UP endpoint URL>`, `data.url = <gateway>` (**verify against the provider you test with** — I did not exercise a live gateway); with this code the gateway has nothing to route to the device by, so push either doesn't reach the client or only works with a provider that routes purely by host. Additionally `sanitize_token` is not injective (`@a.b:hs` and `@a_b:hs` both → `_a_b_hs`), so two accounts can collide in `UpSharedBusQt::routes_` (`LinuxUpConnectorQt.cpp:94-100`) and in the distributor's token table, and the token is guessable by any process that can call `org.unifiedpush.Connector1` (`Message/NewEndpoint/Unregistered` have no caller check; the token is the only secret). Use a random per-registration token (persisted), pass the real endpoint as the pushkey, and key `routes_` by that token.

**M56. Syntax highlighting of received code blocks runs on the UI thread with no input caps**

`ui/shared/views/html_spans.cpp:838-868` (`emit_code_block`) → `tesseract::highlight_code` (`client/src/highlight.cpp:84-108`) → `sdk/src/highlight.rs:84-108`. Every `<pre><code class="language-X">` in an incoming message is highlighted synchronously while the row is built (UI thread), via syntect with the pure-Rust `fancy-regex` engine (`sdk/Cargo.toml:60`, `default-fancy`). There is no cap on code length, line length or line count (an event can carry ~64 KiB), and fancy-regex can backtrack heavily on adversarial input against the bundled Sublime grammars; `highlight_line` returns an error only once its (large) backtrack limit trips, per line. A hostile sender can therefore stall every recipient's UI for the duration (and the result isn't cached until it finishes). Cap input (e.g. ≤ 8 KiB, ≤ 200 lines, ≤ 2 KiB per line → plain monospace beyond that), and move highlighting off the UI thread / behind a time budget. The cache (`highlight.cpp:17`, 256 entries) only helps repeats.
- Status: Partial: capped at 8 KiB, 200 lines and 2 KiB per line; larger blocks stay plain. **Not done:** highlighting off the UI thread

**M58. Remote video is converted YUV→RGBA per pixel on the two tokio worker threads**

`sdk/src/client/rtc/livekit_room.rs:905-933,1176-1200`: for every subscribed remote video/screen track a task runs `NativeVideoStream` and calls `i420_to_rgba` — a scalar per-pixel loop with three bounds-checked index computations and a fresh `w*h*4` `Vec` — for every frame, directly on the SDK runtime, which has only **two** worker threads shared with sync, uploads/downloads and every other room's diff streams (see the "this runtime's only 2 worker threads" comment in `history_export/mod.rs:417`). A 1080p screen share at 30 fps is ~60 M pixels/s per stream; two or three such streams can saturate the runtime and stall Matrix sync/sends for the duration of the call, and the 8 MB RGBA buffer is then converted *again* to BGRA in C++ (`EventHandlerBase.cpp:1075-1127`, M49). Convert off the runtime (`spawn_blocking`/a small dedicated pool), use libwebrtc's SIMD `to_argb`/libyuv instead of the scalar loop, and downscale to the tile size before handing frames to C++. Also: `i420_to_rgba` assumes `stride == width` and `u/v stride == w/2` (`:1183-1196`) and ignores the strides libwebrtc reports; for padded or odd-width frames the picture is skewed/mis-coloured (verify with a stream whose width isn't a multiple of 16).
- Status: Partial: the conversion runs on the blocking pool, one per track. **Not done:** SIMD or libyuv, and downscaling before the frame reaches C++

**M63. Pending attachments (and per-room drafts) hold whole files in RAM with no total cap, and are copied**

`ui/shared/views/media_drop.cpp:5-60`, `ComposeBar.h:294`, `RoomPane.cpp:98-145`: every dropped/pasted file is read completely (up to `kMaxDroppedFileBytes` = 2 GiB per file, see L83) and kept in `ComposeBar::pending_` as a `std::vector<uint8_t>`; up to 20 attachments are accepted, and the per-file upload-limit check is skipped entirely when `media_upload_limit()` returns 0 (unknown). `add_pending_video/audio(bytes, …)` take the vector by const reference and copy it, then the same bytes are copied again for the probe (`probe(std::move(bytes))` after the copy) — three live copies of a large video. `save_compose_draft_` (`RoomPane.cpp:137-144`) moves the pending attachments into `room_compose_drafts_[room_id]`, so switching rooms with attachments queued keeps every room's attachments in memory for the whole session (the map is only erased when a room's composer is empty). **M70. Composer emoji re-sizing is quadratic in the text length and runs on every edit**

`ui/linux-qt/tk/host_qt.cpp:2174-2210` (`reformat_emoji_runs`) runs from the `textChanged` handler (`:1162-1187`), from `replace_range` and from the mention/emoticon insert paths. **M72. A failed bridge-status lookup is cached forever as "not bridged", and the lookups fetch each room's full state in parallel without a bound**

`sdk/src/client/backfill.rs:494-650` (`start_bridge_status_check`): for every room id the shell passes (the visible set, re-sent whenever it changes) the task issues `GET /rooms/{id}/state` — the **entire** room state, including every `m.room.member` event — just to look for `uk.half-shot.bridge` and `com.beeper.room_features`, and spawns all of them into one `JoinSet` with no concurrency limit. Worse, the result of `client.send(...).await.ok().map(..).unwrap_or_default()` (`:579-584`) maps *any* error (429, 5xx, timeout, 403 because the user was just removed) to an empty state, which the task then persists as `is_bridged = 0`. **M77. Saving an attachment fails silently, writes on the UI thread, and cannot open non-ASCII paths on Windows**

`ui/shared/app/RoomPane.cpp:3989-4003` (`save_source_to_file_`): the callback does `if (!bytes.empty()) { std::ofstream f(dest, std::ios::binary); f.write(...); }` with `dest` the UTF-8 `std::string` from the native save dialog. (3) The whole file (up to the cap) is written synchronously on the UI thread. **M82 (Medium on Linux, potentially High on Windows/macOS — verify) — QR-grant waits hold the shared FFI lock for minutes, and the cancel path needs the same lock.** `Client::await_qr_scanned/await_qr_auth/await_qr_complete` (`client/src/client.cpp:222–243`) take `SH_FFI` (a `std::shared_lock`) and block in `rt.block_on(rx)` until the other device scans, the user types the check code and the browser step finishes. `Client::cancel_qr_grant()` and `submit_qr_check_code()` also take `SH_FFI`. The design relies on shared locks never queueing behind a waiting writer (comment at `client.cpp:100`: "never block behind a shared block_on"). That holds for glibc's default reader-preferring `pthread_rwlock`, but not for the Windows SRW lock or libc++/macOS `shared_mutex`, which stop admitting new readers while an exclusive acquirer waits. On those platforms, any `MUT_FFI` call arriving during the wait (this is a logged-in client with sync running, so mut-pool sends, receipts and settings pushes are routine) blocks, and every later `SH_FFI` call — including the UI thread's reads and `cancel_qr_grant()` from `QRGrantView::shutdown()` — queues behind it. `shutdown()` then also `join_worker_()`s a worker that is itself stuck in the await, so closing the dialog hangs the UI thread (deadlock). **D8. Offline banner wording is decided once, when the app goes offline**

`MainAppWidget::set_offline` probes `is_network_available()` only on the offline transition (`handle_offline_ui_` fires on transitions). If the homeserver is down first ("Can't reach the server") and the OS network then drops, the banner is not refreshed until the next transition. Cosmetic.

**D9. GIF without a trailer is unsendable**

`strip_gif` returns `None` when the stream has no `0x3B` trailer; `prepare_image_for_send` then refuses an animated GIF whose metadata "can't be stripped" (message: "This image can't be sent because its metadata can't be removed."). Some encoders omit the trailer and viewers accept such files. Consider accepting EOF-after-last-block as terminated.

**D10. A handled decoder panic may still trigger the crash reporter**

`jxl.rs::guarded` and `strip_meta::strip_checked` use `catch_unwind` (correct, and `Cargo.toml` sets no `panic = "abort"`), but `crash_reporter.rs` installs a `std::panic::set_hook`. Whether a caught malformed-image panic produces a crash report when reporting is enabled was **not verified**; if it does, hostile or corrupt images will generate spurious reports.

**D16. Low — verification-cancel wording**

`EncryptionSetupOverlay::verification_cancelled` maps `m.user` to "The other device cancelled the verification." The SDK reports `m.user` for a user-initiated cancel by either side.
